# Cross-Family SFT / LoRA — FactGuard Rebuttal Experiment

**Goal.** Replicate the paper's Qwen2.5 fine-tuning recipe on **two other model families** to
prove the reliability gains are *not* specific to Qwen (rebuttal to the circularity critique).

- **InternLM2.5 series (a clean 3-size ladder):** 1.8B / 7B / 20B — supports the *scaling*
  argument across a non-Qwen family. Native context **32K**.
- **GLM-4:** 9B (native **128K**) + 32B-0414 (native 32K) — GLM-4-9B-chat is the strongest
  *native-long-context* cross-family point.

All hyperparameters are **identical to the paper** (§Implementation Details):

| Method | optimizer | lr | epochs | warmup | weight_decay | LoRA |
|--------|-----------|----|--------|--------|--------------|------|
| Full SFT | AdamW | 2e-5 | 2 | 0.1 | 0.1 | — |
| LoRA | AdamW | 2e-5 | 2 | 0.1 | 0.1 | rank=8, α=16, target=query/value |

> Effective batch size = `per_device_train_batch_size(1) × grad_accum(16) × #GPUs`.
> The paper does not state batch size; adjust `gradient_accumulation_steps` to match your
> preferred effective batch if you want strict parity across model sizes.

## Run

```bash
cd factguard_code

# 1) build the training set once (path defaults to ./data/merged_train.jsonl)
TRAIN_SRC=/abs/path/to/merged_train.jsonl bash train/run_train.sh prepare

# 2a) a single experiment
bash train/run_train.sh internlm2_5_7b sft
bash train/run_train.sh glm4_9b lora

# 2b) everything, sequentially (10 runs: 5 models × {sft,lora})
bash train/run_train.sh all

# limit GPUs for one run:
CUDA_VISIBLE_DEVICES=0,1,2,3 bash train/run_train.sh internlm2_5_20b sft
```

Outputs (checkpoints + `.log` + loss plot) land in `train/output/<model>_<method>/`.

## ⚠️ Important caveats before you launch

1. **Context length / VRAM.** `cutoff_len` is set to each model's **native** window:
   InternLM2.5 = 32768, GLM-4-9B = 131072, GLM-4-32B = 32768. Training at 128K is extremely
   memory-heavy. If you OOM:
   - Lower `cutoff_len` (e.g. 32768 or 16384). The paper's train split is mostly ≤32K anyway
     (see paper Table 1), so 32K captures the bulk of the data.
   - Full SFT of 20B/32B needs ZeRO-3 + offload (already wired via `ds_z3_offload.json`) and
     ideally ≥8×A100-80G. LoRA fits far more easily.

2. **InternLM2.5 native context is 32K, not 128K.** This is a *known* trade-off (no non-Qwen
   family offers a clean multi-size 128K-native ladder). Two honest options for the paper:
   - Report InternLM2.5 as a **32K-native** cross-family scaling check (recommended, simplest), OR
   - Extend RoPE to 128K and say so explicitly. To extend, add to the YAML:
     ```yaml
     rope_scaling: yarn      # or: dynamic
     # then raise cutoff_len to 131072
     ```
   Do **not** silently train InternLM2.5 above 32K without noting the extension.

3. **Chat templates must be correct** (or the model learns garbage):
   - InternLM2.5 → `template: intern2`
   - GLM-4 → `template: glm4`
   Both are pinned in the YAMLs; verify your LLaMA-Factory version recognizes these names
   (`llamafactory-cli train -h` / check `src/llamafactory/data/template.py`).

4. **LoRA target modules.** The paper targets **query & value** projections. These arches fuse
   QKV into a single matrix, so we target the fused projection:
   - InternLM2.5 → `wqkv`
   - GLM-4 → `query_key_value`
   This includes K as well (unavoidable with fused QKV). If you want to match "q,v only"
   more strictly, use `lora_target: all` and rely on the paper's rank=8 as the key knob, or
   split the fused weight — but fused-QKV LoRA is the standard, defensible choice; just state
   it in the paper.

5. **`merged_train.jsonl` schema.** Fields used: `input` (Document+Question), `output`
   (answer / reasoned rejection). `prepare_data.py` maps them to alpaca
   `{instruction:"", input, output}`. 19,100 rows = paper's Train split.

## After training → evaluate

Reuse the paper's existing eval pipeline (unchanged, so numbers are comparable to the
Qwen results):

1. Generate predictions on the FactGuard-Bench **test set** with each fine-tuned checkpoint
   (vLLM/HF generate; same prompt format as `input`).
2. Score with the Qwen2.5-72B LLM-judge: `misa/cli/evaluate.py`.
3. Aggregate per En/Zh × Ans./Lack./Mis. and length buckets: `compute_metrics.py`.
4. (Also strengthens the rebuttal) cross-judge check with `compare_judges.py`.

Produce one table: **each family, before vs after SFT/LoRA**, mirroring paper Table 3 —
that is the direct answer to "does it generalize beyond Qwen?".
